# Гайд для агента: база знаний ortopol

Ты подключён к развёрнутой из этого пакета базе — корпусу работ И. И. Шарапудинова
(68 источников, ~2500 страниц; в профиле `public` часть документов представлена
только метаданными и векторами — см. «Профиль пакета») и хранилищу результатов численных экспериментов над
дискретными ортогональными полиномами. Этот файл самодостаточен: всё, на что он
ссылается, находится либо в этой базе, либо в самом пакете (`docker-compose.yml`,
`.pgenv.example`, `init/`, `smoke_test.py` и соседние скрипты — все распакованы рядом
с этим файлом). Файлов родительского репозитория (`theory/`, `corpus_completeness.py`
и т.п.) на этой машине нет и ссылаться на них бессмысленно.

## Подключение

Пакет поднимает два сервиса: `kb-pg` (Postgres 17 + pgvector; какие схемы —
зависит от профиля пакета, см. «Профиль пакета» ниже: `corpus` всегда,
`measurements` только в профиле `full`) и `kb-ollama` (модель `bge-m3` для
эмбеддингов запросов).

```bash
tar --zstd -xf kb-<профиль>-<дата>.tar.zst -C kb-current
cd kb-current                   # ВСЁ (compose, дамп, скрипты) лежит здесь плоско
cp .pgenv.example .pgenv        # заполнить PGPASSWORD реальным значением
docker compose --env-file .pgenv -p kb up -d
```

Формат `.pgenv` — плоский `KEY=VALUE`, без `export`. `KB_PG_PORT` — единственный
источник истины для порта: `PGPORT` в `.pgenv.example` ссылается на него
(`PGPORT=$KB_PG_PORT`), а не дублирует число, так что смена одной переменной
меняет обе стороны разом:

```
PGUSER=ortopol
PGDATABASE=ortopol
PGPASSWORD=...
KB_PG_PORT=5472
KB_OLLAMA_PORT=5473
KB_ARTIFACT_DIR=.
KB_EMBED_MODEL=bge-m3
PGHOST=127.0.0.1
PGPORT=$KB_PG_PORT
```

Подключение к базе — обычный `psql` (или любой Postgres-клиент) после
`set -a; . .pgenv; set +a` (bash-источник резолвит `$KB_PG_PORT`; docker
compose своим `--env-file` не разворачивает `$` и до `PGPORT` не
дотрагивается вовсе — переменные не конфликтуют). Порт ollama (по умолчанию
5473) публикует `POST /api/embed`, `{"model": "bge-m3", "input": "текст"}` →
`{"embeddings": [[...]]}`.

## Самопроверка развёртывания

Пакет несёт собственный смок-тест: `smoke_test.py` и модули, которые он
импортирует (`smoke_stack.py`, `smoke_checks.py`, `vector_probe_check.py`,
`blob_integrity_checks.py`, `bundled_files_check.py`, `manifest_contract.py`,
`compose_lifecycle.py`, `dump_integrity.py`, `deploy_pathfix.py`,
`ollama_registry.py`, `drift_probe.py`, `profile_checks.py`, `dump_scan.py`,
`pg_rank_probe.py`), а также копии
двух общих модулей репозитория (`corpus_lib/pg_common.py`,
`corpus_lib/pg_search.py`) лежат прямо здесь, рядом
с дампом и `manifest.json` — запускаются без доступа к репозиторию:

```bash
python3 smoke_test.py
```

Без аргументов скрипт берёт `manifest.json`/`01_dump.sql.gz` из своей же
директории, поднимает временный стек на портах 5474/5475 (не пересекается с
портами выше), сверяет каждый пункт манифеста и сносит стек. Проверка «живой
инстанс не задет» в этом режиме помечается `SKIP` — у самодостаточного пакета
нет доступа к чужому «живому» инстансу для сверки, это ожидаемо, а не пробел.

## Профиль пакета: что в нём есть и почему чего-то нет

`manifest.json` → `profile`. Профиля два, и разница видна в данных, поэтому её надо
знать ДО того, как делать вывод «база неполна»:

- **`full`** — все схемы (`corpus` + `measurements`), полный текст каждой страницы,
  исходный PDF/djvu каждого документа. Этот профиль не публикуется.
- **`public`** — только схема `corpus`, и содержимое урезано по правовому режиму
  документа. Режим лежит В САМОЙ БАЗЕ, у каждой строки:

  ```sql
  SELECT legal_class, public_distribution, legal_note, length(source_blob)
  FROM corpus.documents WHERE id = 'название_документа';
  ```

  - `public_distribution = 'full-text'` или `'internal'` — документ целиком: текст
    страниц, `tsv`, вектор, `source_blob`.
  - `public_distribution = 'metadata-only'` — строка документа есть (с
    `legal_class`/`legal_note`, откуда видно основание), `source_blob` = `NULL`,
    страницы есть все, но у них `body = ''` (значит и `tsv` пустой) и только
    `page_number` + `embedding`.

  Практическое следствие: **такой документ находится векторным поиском и не
  находится fulltext'ом**, а прочитать его текст здесь нельзя — идти по `source_url`
  к издателю. Это правовая граница, а не потеря данных: `pages_count`,
  `chars_extracted`, `source_sha256` на месте, так что собственный, легально
  полученный экземпляр PDF сверяется по хешу.

  `measurements` в этом профиле отсутствует целиком — результаты наших измерений
  распространяются отдельным артефактом. Смок-тест помечает соответствующую
  проверку `SKIP`, а не `FAIL`.

Состав можно проверить, ничего не разворачивая, — по самому артефакту:

```bash
python3 profile_checks.py            # рядом с manifest.json/01_dump.sql.gz
```

Скрипт читает дамп и сверяет с манифестом: схемы, полноту правовой классификации
(`legal.unclassified_documents` = 0 и каждый документ дампа назван ровно в одном
классе), отсутствие блоба и текста у всех `metadata-only`, наличие того и другого у
всех остальных, наличие вектора у каждой страницы. Exit 0 — состав соответствует
заявленному профилю.

## Три режима поиска — и когда какой

В базе нет отдельного инструмента поиска (в этом пакете), но все три режима — это
готовые SQL-запросы, без внешних зависимостей.

**1. Fulltext** (`corpus.pages.tsv`, конфигурация `'russian'`) — когда известна точная
формулировка или её словоформа. `phraseto_tsquery` требует, чтобы леммы шли подряд
(фразовое совпадение, не «все слова где-то на странице»), а конфигурация `'russian'`
(не `'simple'`) снимает стемминг: запрос «повторных» находит страницу с «повторные».

```sql
SELECT d.id, p.page_number, left(p.body, 200)
FROM corpus.pages p JOIN corpus.documents d ON d.id = p.document_id
WHERE p.tsv @@ phraseto_tsquery('russian', 'повторные средние')
ORDER BY d.id, p.page_number;
```

**2. Vector** (`corpus.pages.embedding`, 1024 измерения, косинусная дистанция, HNSW) —
когда нужного слова не знаешь или страница выражает мысль другими словами. Запрос
обязан быть эмбеддирован **той же моделью**, что и хранимые векторы — см. ниже
«Правило одной модели».

```sql
SELECT d.id, p.page_number, left(p.body, 200)
FROM corpus.pages p JOIN corpus.documents d ON d.id = p.document_id
WHERE p.embedding IS NOT NULL
ORDER BY p.embedding <=> '[0.01, ...]'::vector   -- вектор запроса из /api/embed
LIMIT 20;
```

**3. Hybrid** (Reciprocal Rank Fusion, K=60) — по умолчанию, когда неясно, какой из
двух режимов лучше подойдёт: ранги обоих списков совместимы по шкале (в отличие от
сырых ts_rank и cosine distance), документ, найденный обоими, побеждает.

```sql
WITH ft AS (
    SELECT p.id, row_number() OVER (ORDER BY ts_rank(p.tsv, q.query) DESC) AS rnk
    FROM corpus.pages p, phraseto_tsquery('russian', :'q') AS q(query)
    WHERE p.tsv @@ q.query LIMIT 100
), vec AS (
    SELECT p.id, row_number() OVER (ORDER BY p.embedding <=> :'vec'::vector) AS rnk
    FROM corpus.pages p WHERE p.embedding IS NOT NULL LIMIT 100
)
SELECT d.id, p.page_number, left(p.body, 200)
FROM corpus.pages p
JOIN corpus.documents d ON d.id = p.document_id
LEFT JOIN ft ON ft.id = p.id LEFT JOIN vec ON vec.id = p.id
WHERE ft.id IS NOT NULL OR vec.id IS NOT NULL
ORDER BY coalesce(1.0/(60+ft.rnk),0) + coalesce(1.0/(60+vec.rnk),0) DESC
LIMIT 20;
```

## Правило одной модели

`corpus.embedding_model` (одна строка) называет модель и размерность, которыми
посчитаны ВСЕ векторы в `corpus.pages.embedding`:

```sql
SELECT model, dims FROM corpus.embedding_model;   -- bge-m3, 1024
```

Эмбеддинг запроса **другой** моделью (или той же модели другой версии) даёт вектор
той же размерности — cosine distance посчитается без ошибки и вернёт правдоподобный,
но бессмысленный результат: расстояние в чужом векторном пространстве не про смысл.
Перед вызовом `/api/embed` сверяй `model` из этой таблицы, не полагайся на память.
Если у ollama другая модель по умолчанию — указывай `bge-m3` явно в `"model"`.

## Семантика доверия: `extraction_state`

У каждого документа (`corpus.documents.extraction_state`) — ярус доверия страницам:

| Значение | Что это | Что можно делать |
| --- | --- | --- |
| `clean` | Извлечено из PDF-текстового слоя механически, без потерь | Цитировать текст напрямую |
| `recoded` | Как `clean`, но потребовалась перекодировка (напр. cp1251-as-latin1 mojibake) | Цитировать текст напрямую |
| `degraded` | Читаемо, известные точечные потери (типично: лигатуры ff/fi без ToUnicode, ~0.3% слов) — масштаб потерь в `note` | Цитировать текст; на редком слове с выпавшей лигатурой — свериться с изображением |
| `transcribed` | Прочитано моделью с отрисовки страницы, формулы — в LaTeX (лучше механического извлечения там, где формулы выносные) | **Перед использованием в коде/выводе сверить формулу с изображением страницы** — модель транскрипции может дать правдоподобную, но неверную деталь |
| `ocr` | Чужой слой распознавания (напр. из djvu), ошибки есть и не измерены | Использовать только как черновой ориентир; не цитировать дословно без сверки |
| `metadata` | Курируемое нами описание корпуса (не статья ИИШ) | Справочно |
| `unreadable` | Строка-заглушка: содержимое недоступно ни в каком виде | Не источник текста; сам факт присутствия — часть учёта полноты корпуса |

`note` на документе, когда есть, называет конкретную оговорку (пример из этой базы:
`"readable text with known losses: ... ~0.3% of words"`).

Страница без семантического текста (`body` пустой/whitespace) не имеет `embedding` —
это ожидаемо, не повреждение.

## Пруф-чтение источника: `source_blob`

`source_path` (генерируемая колонка вида `theory/iis/<файл>`) указывает на путь
**в исходном репозитории разработки** — на этой машине такого пути нет и обращаться
к нему как к файлу нельзя. Вместо этого сам источник (PDF/djvu) лежит в базе:

```sql
SELECT source_blob, source_sha256, length(source_blob)
FROM corpus.documents WHERE id = 'название_документа';
```

Чтобы свериться с изображением страницы (обязательно для `transcribed`, разумно для
любой цитаты из выносной формулы): извлечь `source_blob` в файл, проверить
`sha256(файл) = source_sha256` (несовпадение — файл на диске подменён/повреждён
относительно того, что видела транскрипция — не игнорировать, а разбираться), затем
отрендерить нужную страницу (`pdftoppm -r 150 -png` для PDF, `ddjvu` для djvu) и
прочитать её глазами/зрительной моделью. `source_url` (когда не `NULL`) — канонический
адрес публикации (Math-Net.Ru и т.п.) для внешней проверки, независимой от этой базы.

## Хранилище измерений

`measurements.run` — один прогон исследования = одна строка. Обязательные для
доверия поля:

- `question` — что проверялось;
- `arbiter` — как определялось «согласуется/не согласуется»;
- `reproduce` — команда, пересоздающая данные с нуля (не гарантированно исполнима
  на этой машине без остального репозитория — но описывает метод);
- `verify_query` — как вывод переспрашивается против **уже имеющихся** данных;
  находка есть цитата этого запроса, а не пересказ;
- `rules_out` — что результат исключает; для отрицательного результата это вся
  ценность записи — база хранит провалившиеся гипотезы наравне с подтвердившимися,
  чтобы их не переоткрывали за те же деньги;
- `source_tier` + `our_stance` — внешний факт записан как «источник X утверждает Y»,
  никогда как решённое `Y`; `our_stance = 'relied-upon'` означает, что кто-то из
  людей сверил это с первоисточником, `'to-verify'` — что пока нет;
- `family` / `area` / `varied` — фасеты для навигации (`family && array['tchebichef']`
  и т.п.);
- `embedding` — тот же bge-m3/1024, находится тем же vector/hybrid запросом, что и
  страницы (JOIN не нужен — таблица самостоятельна).

Точечные числа каждого эксперимента — в отдельной таблице `measurements.<имя>`
(например `error_surface`, `meixner_gram_defect`, `derivative_edge_magnitude`),
внешний ключ на `measurements.run.id`. Список таких таблиц — не фиксирован: они
добавляются по мере новых замеров.

```sql
SELECT id, question, verdict, rules_out FROM measurements.run
WHERE family && array['meixner'];
```

## Чего в базе НЕТ

В профиле `public` нет текста и исходников документов с
`public_distribution = 'metadata-only'` (см. «Профиль пакета») и нет схемы
`measurements` — оба пропуска объявлены в `manifest.json` и проверяются
`profile_checks.py`, то есть это известные границы, а не повреждение.

Это не курируемый реестр проверенных утверждений — `measurements.run.our_stance`
маркирует уверенность конкретной записи, но нет отдельной таблицы «фактов, которым
можно доверять без дополнительной проверки». Каждая находка (fulltext/vector/hybrid
хит, строка `measurements.run`) — это цитата конкретного места в конкретном
источнике или конкретного прогона, а не готовый вывод: перепроверка контекста
(соседние страницы, `our_stance`, `extraction_state` страницы-источника) остаётся
на агенте, который эту находку использует.

## Проверка целостности своими силами

Если есть основания подозревать само развёртывание (не отдельную находку) —
целостность проверяется теми же SQL-запросами, что приведены выше, без
дополнительных инструментов: количество документов/страниц (`corpus.documents`,
`corpus.pages`), что fulltext и vector находят ожидаемое, что `embedding_model`
согласована с фактической размерностью векторов (`vector_dims(embedding)`), что
`measurements.run` заполнена по всем обязательным полям, и что блоб источника
round-trip'ится побайтно — извлечь `source_blob`, посчитать `sha256`, сравнить с
`source_sha256`; расхождение означает повреждённое развёртывание, а не находку,
которой можно доверять с оговоркой.
